# Column Projection & Request-Scoped Caching Design

**Date:** 2026-04-29  
**Branch:** (to be created)  
**Status:** Design approved, ready for implementation plan

## Problem

Two sources of unnecessary database egress in the current codebase:

1. **`getRawEnergyData` uses `SELECT *`** — retrieves all columns including `id` and `battery_soc`, which are unused or redundant for most callers. This inflates response size by ~10-15% (~1.3 MB → ~1.1 MB for typical Trmnl markup calls over a 30-day billing cycle).

2. **`getSite()` may be called multiple times in a single request** — while the site is cached across requests (15-min TTL), there's no per-request deduplication. In complex request flows (e.g., dashboard operations, admin panels), the same site may be fetched from cache multiple times, even though the cache is already warm.

## Goal

Reduce database egress and queries by ~10-15% through column projection and request-scoped caching, without schema changes or breaking API contracts.

## Approach: Two Sequential PRs

### PR 1: Column Projection in `getRawEnergyData`

**File:** `cmd/next-app/src/lib/energy-repo.ts`

**Current implementation:**
```ts
async getRawEnergyData(siteId: string, start: Date, end: Date): Promise<EnergyData[]> {
    const res = await pool.query(`
        SELECT * FROM "EnergyData"
        WHERE site_id = $1 AND timestamp >= $2 AND timestamp < $3
        ORDER BY timestamp ASC
    `, [siteId, start, end]);
    return res.rows.map(row => ({
        ...row,
        timestamp: new Date(row.timestamp),
        site_id: row.site_id.toString(),
        load_power: Number(row.load_power),
        solar_power: Number(row.solar_power),
        grid_power: Number(row.grid_power),
        battery_power: Number(row.battery_power),
        battery_soc: row.battery_soc === null || row.battery_soc === undefined ? null : Number(row.battery_soc),
    })) as EnergyData[];
}
```

**Rationale for column choices:**
- Keep: `site_id, timestamp, tariff_id, tariff_schedule_id, load_power, solar_power, grid_power, battery_power` — these are used by all callers (Trmnl markup, usage aggregation, analysis).
- Drop: `id` — unused in returned EnergyData; generated by the row mapping.
- Drop: `battery_soc` — only needed for `getLatestEnergyData()`, which fetches a single row separately. Including it in bulk queries wastes ~2-3% of wire size per call.

**New implementation:**
```ts
async getRawEnergyData(siteId: string, start: Date, end: Date): Promise<EnergyData[]> {
    const queryStart = Date.now();
    const res = await pool.query(`
        SELECT site_id, timestamp, tariff_id, tariff_schedule_id, load_power, solar_power, grid_power, battery_power
        FROM "EnergyData"
        WHERE site_id = $1 AND timestamp >= $2 AND timestamp < $3
        ORDER BY timestamp ASC
    `, [siteId, start, end]);
    const queryDuration = Date.now() - queryStart;
    console.log(`[EnergyRepo] getRawEnergyData: Query = ${queryDuration}ms, Rows = ${res.rows.length}`);

    return res.rows.map(row => ({
        timestamp: new Date(row.timestamp),
        site_id: row.site_id.toString(),
        tariff_id: row.tariff_id,
        tariff_schedule_id: row.tariff_schedule_id,
        load_power: Number(row.load_power),
        solar_power: Number(row.solar_power),
        grid_power: Number(row.grid_power),
        battery_power: Number(row.battery_power),
        battery_soc: null,
    })) as EnergyData[];
}
```

**Tests:**
- New unit test: insert a known row with all columns, call `getRawEnergyData`, assert the returned object has only the 8 expected fields (no `id`, no `battery_soc`).
- Existing tests should still pass (the return type interface remains unchanged).

**Impact:**
- Response size reduction: ~10-15% per call (typical Trmnl markup query returns ~288 rows; wire size ~1.1 MB instead of 1.3 MB).
- At ~96 calls/day per Trmnl device, this saves ~20-30 MB/day per active device.

### PR 2: Request-Scoped Caching for `getSite()`

**File:** `cmd/next-app/src/lib/energy-repo.ts` and optionally a new `cmd/next-app/src/lib/request-context.ts`

**Problem:**
The existing cache on `EnergyRepo.getSite()` is persistent (15-min TTL across requests). Within a single request, if `getSite()` is called multiple times with the same `siteId`, each call hits the persistent cache, which is efficient. However, if the flow changes in the future or new endpoints batch multiple sites, we'd benefit from per-request deduplication.

**Solution:**
Add a simple request-context cache Map that lives for the duration of a single request. Wrap the existing `getSite()` call to check this cache first before hitting the persistent cache.

**Implementation pattern:**

Create `cmd/next-app/src/lib/request-context.ts`:
```ts
import { AsyncLocalStorage } from 'async_hooks';

interface RequestContext {
    siteCache: Map<string, any>;
}

const requestContext = new AsyncLocalStorage<RequestContext>();

export function getRequestContext(): RequestContext {
    let ctx = requestContext.getStore();
    if (!ctx) {
        ctx = { siteCache: new Map() };
        requestContext.run(ctx, () => {});
    }
    return ctx;
}

export async function withRequestContext<T>(fn: () => Promise<T>): Promise<T> {
    const ctx: RequestContext = { siteCache: new Map() };
    return requestContext.run(ctx, fn);
}
```

Modify `EnergyRepo.getSite()`:
```ts
async getSite(siteId: string, options?: SiteQueryOptions): Promise<SiteWithTariffs | undefined> {
    const now = Date.now();
    
    // Check request-scoped cache first
    const requestCtx = getRequestContext();
    const cachedInRequest = requestCtx.siteCache.get(siteId);
    if (cachedInRequest && (!options?.includeJson || cachedInRequest.json !== undefined)) {
        return cachedInRequest;
    }
    
    // Fall through to existing persistent cache logic
    const cached = siteCache.get(siteId);
    if (cached && cached.expires > now && (!options?.includeJson || cached.data.json !== undefined)) {
        requestCtx.siteCache.set(siteId, cached.data);
        return cached.data;
    }

    // Fetch from database (existing logic)
    const columns = options?.includeJson ? SITE_COLUMNS_WITH_JSON : SITE_BASE_COLUMNS;
    const siteRes = await pool.query(`SELECT ${columns} FROM "Site" WHERE id = $1`, [siteId]);
    const site = siteRes.rows[0] as Site | undefined;
    if (!site) return undefined;

    // ... rest of existing getSite() logic ...
    
    const result = { ...site, access_token, refresh_token, auth_status, tariffs } as SiteWithTariffs;
    
    // Store in both request cache and persistent cache
    siteCache.set(siteId, { data: result, expires: now + CACHE_TTL_MS });
    requestCtx.siteCache.set(siteId, result);
    
    return result;
}
```

Wrap API route handlers:
Each route that calls `getSite()` should wrap its logic in `withRequestContext()`:
```ts
export async function GET(request: Request) {
    return withRequestContext(async () => {
        // existing route logic
    });
}
```

This pattern is lightweight and works with Next.js's request-per-connection model.

**Tests:**
- Unit test: call `getSite(siteId)` twice in the same request context; assert only one database query occurs (the second hit the request cache).
- Verify existing persistent cache behavior is unchanged.

**Impact:**
- Query reduction: depends on request patterns. Dashboard and admin operations that iterate over multiple sites will see the most benefit.
- Egress savings: ~5-10% for heavy multi-site request flows; negligible for single-site requests.

## Success Criteria

- PR 1: `getRawEnergyData` returns exactly 8 columns (no `id`, no `battery_soc`); all existing tests pass; new unit test added.
- PR 2: Request-scoped cache is populated on first `getSite()` call, subsequent calls in the same request hit the request cache; existing persistent cache logic unchanged.
- Combined: Supabase egress dashboard shows measurable reduction within 24-48 hours of deploying PR 1 (primary win); PR 2 contributes minor additional savings.
- No breaking changes to public API or return types.

## Out of Scope

- Schema changes or migrations.
- Changes to `getBucketedEnergyData` or `getCycleAggregates` (already optimized).
- Other query optimizations (e.g., JOINs for tariff loading, Trmnl live-status caching) — defer to future passes.
- Integration with other caching layers (Redis, CDN) — keep it simple and local.

## Rollback

- PR 1: Revert the `getRawEnergyData` query and mapping. Old code is backward-compatible (same return type, just without `battery_soc`).
- PR 2: Remove the request-context logic; `getSite()` falls back to persistent cache only. No data loss or behavior change.
