# Site history onboarding design

## Goal

Give a newly connected site useful recent history without blocking the user, then seek enough evidence for an automatic solar layout. The device owns and resumes the work; the server proxies Tesla requests and stores shared history. The earlier 2026-10-27 discussion is historical context, not an authorization for a server-side full-history worker or tariff-history reconstruction.

## Import and scheduling

Start a site-scoped job when an eligible site is connected, and reconcile existing sites with missing history when encountered. Scope persisted state by account and site; cancel or isolate work on sign-out, account change and site change. Use site-local complete days and honor installation and `history_backfill_from` boundaries. Check recent 14 days first, then proceed newest first, subject to a one-year maximum. A 90-day window is an initial checkpoint, not a promise of success or a mandatory minimum: a usable layout may end the solar-specific extension earlier. Recent history still receives priority even if a layout already exists.

Use short, fixed site-local date slices (initially at most three complete days). The phone stores one cursor: the oldest fully checked slice. Each request asks the server to ensure that exact slice; advance the cursor only when the whole slice returns `complete`. On timeout, busy lock, partial result, cancellation or lost response, retry the same slice. The importer re-audits stored coverage, so successfully stored days are skipped on retry. This gives bounded, resumable work without a per-day job ledger or per-day progress protocol. Keep slices outside the trailing 14 days behind recent-history priority; leave routine recent gap retries to gap healing. Honor existing importer coverage checks, per-site locking, token handling and request budgets. Use backoff for transient failures and throttling, and pause with a clear action for authentication failures. Do not assume iOS will run a background task on schedule or after force-quit; resume on foreground and on granted background opportunities. Ensure fairness and limits for multiple sites and devices.

The existing `/api/sync` streams responses and has a 40-second server budget. Prefer a small authenticated mobile JSON endpoint that accepts a site ID and a bounded pair of site-local dates, validates the installation boundary (the one-year maximum is the phone's onboarding policy, not a server limit, so later full-history features can reuse the fill), and calls `ensureDataForRange` with a short time/window cap. Return `complete`, `partial`, `busy` or an actionable error for the entire slice; never use progress strings as state. A complete result also covers a slice whose days were already stored or settled empty. The phone computes checked days from its confirmed cursor and available solar days from the existing solar-history sync. No Tesla credentials move to the phone. Recent 14-day healing remains an independent server maintenance function, not the onboarding scheduler.

## Detector feedback

Extract a shared, cheap readiness assessment from the detector's actual producing-day rules; currently 42 producing days are required to attempt detection. It must use the same site-local day semantics as detection, without duplicating thresholds. This gate cannot determine clear days or confidence. At meaningful checkpoints, sync newly archived solar history to the device and invoke the existing detector; use its result and reasons to decide whether additional history is likely to help. A usable medium- or high-confidence layout ends the solar-specific backfill. Insufficient history or evidence can lead to another bounded batch, up to one year or available history; location, auth and other non-history problems must not drive an endless import. Audit the current `few-clear-days` reason, which covers multiple early exits, and introduce more precise typed feedback if needed rather than guessing.

Allow a significant new history batch to trigger reassessment during onboarding without waiting for the normal 30-day low-confidence retry cadence; deduplicate runs and preserve cancellation, location and account-generation safeguards. Do not rerun the expensive fit for every day. Missing location or non-solar sites must not block basic recent history import; show an accurate state and do not claim a solar layout was found.

## Experience

The user can use the app immediately. While the selected site's import is active, an iOS 26 tab-view bottom accessory shows “Loading history for Solar Forecasting” and days checked, without a denominator that changes as the search extends. Tapping opens Site history in Settings. The accessory disappears when the job stops, including completion or an actionable pause; the permanent Settings row remains.

The detail screen shows the checked range, checked days versus days with available data, current state, and understandable detector feedback. A 90-day checkpoint is not a guarantee. If the installation is recent, history is empty, location is missing, or the one-year limit is reached, say what is known and what happens next. Accessible labels and compact placement must work with Dynamic Type and VoiceOver; support the app's sidebar and demo mode appropriately.

Import does not proactively refresh Smart Shift or expected bill; those views pick up data when their tabs are visited. Keep forecasting and the ordinary solar-layout schedule functional independently of onboarding. Future full-history or ROI work can reuse the status and job concepts but is not in scope; imported energy history does not imply historically accurate tariffs.

## Verification

Exercise readiness and detector feedback, checkpoint and stop decisions, local-calendar/DST boundaries, installation and pre-provisioning bounds, settled empty days, partial/busy requests, retries, throttling, cancellation, relaunch, account/site isolation and overlapping gap healing. Test background expiration and foreground resume, detection rerun and deduplication, navigation/accessibility states, and tab-specific refresh. Verify a new site end to end using controlled data, including a cloudy or unavailable-history case. Follow repository iOS formatting, strict SwiftLint and `run-tests.sh` rules, and Next.js lint, tests and build where changed.

## Revised solar-history contract and Tesla throttling

Use the existing solar-history resource for explicit bounded fill requests and return the resulting daily records with whole-range completion status. Ordinary GET reads remain read-only. Replace the unfinished separate history-backfill endpoint with this integrated contract.

For a fill request, propagate Tesla rate limiting as HTTP 529 and include `Retry-After` derived from Tesla's response. Preserve the upstream retry deadline through typed Tesla-client and importer errors; do not reduce it to a generic 500, partial success, or progress string. Stop starting further Tesla requests in that fill operation immediately on throttling, including when earlier days were successfully stored. The existing client retries 429 internally and caps its parsed delay; this path must instead surface throttling promptly and preserve Tesla's actual wait. Normalize HTTP-date or delta-seconds safely; if Tesla omits a valid delay, use a documented fallback and identify it as a fallback.

The device persists the retry deadline for the relevant Tesla account and honors it across foreground/background work, site changes within that account, and relaunch. It must not retry before the deadline; iOS may resume later. Keep the range cursor unchanged after a 529 and retry the same range when eligible, letting stored coverage skip successful days. Display a waiting state in Settings rather than a failed import or a reconnect request. Test 429-to-529 mapping, supplied delta-seconds and HTTP-date delays, waits longer than the existing client cap, missing/invalid headers, throttling after partial writes, and persisted device scheduling.

### Implemented fill contract

`POST /api/mobile/solar-history` with `{ siteId, from: "YYYY-MM-DD", days: 1-3 }` fills complete site-local days `[from, from + days)`; the range must end by today. The server sets no lookback limit; `historyStart` bounds it, and the one-year onboarding maximum is enforced on the phone. Same auth and beta gate as GET (`enabled: false` imports nothing). A 200 answers `{ version, enabled, timeZone, status, historyStart, days }`: `status` is `complete`, `partial` (budget ran out) or `busy` (another import holds the site lock); `days` are the stored records for the slice in GET's day format; `historyStart` is the later of the installation day and `history_backfill_from`, and a slice wholly before it is `complete` without calling Tesla. One fill makes at most three day fetches (energy + SOE each, so at most six Tesla requests) within a 15-second budget.

Failures: 529 `TESLA_RATE_LIMITED` with `Retry-After` (whole seconds, rounded up) and `retryAt`/`retryAfterSource` (`header` or `fallback`; the fallback is 60 seconds, and header waits are capped at one day); 409 `TESLA_CONNECTION_REQUIRED`; 503 `TESLA_REFRESH_BACKOFF` with `Retry-After`; 400 for invalid input; 500 otherwise. The fill's Tesla client runs with `rateLimit: 'surface'`, so the first 429 throws `TeslaRateLimitError` without in-process sleeps, and the importer stops the run on it even after earlier days were written.

### Implemented readiness and feedback

`SolarLayoutDetector.readiness(samples:latitude:longitude:timeZone:)` applies only the detector's producing-day gate (`minHistoryDays`, currently 42) to the synced samples, using the same `producingDays(in:)` rule and series construction as detection; it runs no clear-day selection or fit. A stored day counts only if it produced after the night baseline is removed, so readiness takes samples, not a day count. Onboarding calls it after each synced batch and runs the full detector only once it passes and at later checkpoints, never per slice.

The audit of `few-clear-days` found three distinct early exits (under 200 clear samples; under 200 samples or 5 days after the shade mask; no plane-count fit) in addition to the assessed `clearDays < 15` reason. `reasons` keeps the reference labels for parity; the phone-only optional `DetectedSolarLayout.shortfall` records which early exit stopped a run (`few-producing-days`, `no-daylight-production`, `few-clear-samples`, `few-usable-clear-days`, `no-plane-fit`). `SolarLayoutDetector.historyOutlook` classifies a result as `usable` (forecastable high/medium), `moreHistoryMayHelp` (too few producing, clear or usable days, `few-clear-days`, or `azimuth-uncertain`) or `needsOtherAction` (no daylight production, no plane fit, `location-mismatch`, tilt at the model limit alone, or failure). Results stored before `shortfall` existed decode with it nil and fall back to status and reasons.
